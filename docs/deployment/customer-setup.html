IMMS — Customer Instance Setup Guide

Standing up a new, isolated customer deployment of the Inventory Management System + Maintenance Call System.

Operational runbook · Version 1.0 · Generated 2026‑07‑05 · Companion to docs/deployment/PROD_OPERATIONS.md

Who this is for

The person provisioning a fresh instance for a new customer — one dedicated host (physical box or cloud VM) running its own PostgreSQL database, isolated from every other customer. Each customer gets their own database, their own secrets, and their own processes. This is the manual procedure using today's tooling; fully-automated per-customer provisioning is a planned increment (see Roadmap notes).

1. What you are deploying

One customer instance is five long-running processes plus one database, all on a single host:

ComponentDefault portPurpose
IMMS API4000Inventory, parts, machines, purchase orders, work orders, analytics. The sole login authority.
MCS API4001Maintenance Call System — call board, badge swipes, technician calls.
IMMS UI (local)3002React frontend for the PC/kiosk with a camera.
IMMS UI (network)3001React frontend served to networked displays (e.g. a Raspberry Pi kiosk).
MCS UI3003Next.js call-board frontend.
PostgreSQL5432One database per customer (e.g. imms_<customer>). Shared by IMMS and MCS.

IMMS and MCS share one database and one JWT_SECRET: MCS redirects to the IMMS login page and trusts the JWT it receives back. Keep those two values in lockstep across both apps.

2. Prerequisites

  • Host: a dedicated Windows machine or VM (the reference deployment is Windows 10/11 + PM2). One host per customer — never colocate a customer with development or another customer.
  • Node.js 22.x (matches the CI/runtime target) and npm.
  • PostgreSQL 14+ reachable locally, with a superuser or a role that can create databases.
  • PM2 (npm i -g pm2) for process supervision + boot resurrection.
  • Git, and network access to the application repository.
  • Decide the customer's identifier (used in the DB name and hostnames) and which URLs/IPs the frontends will be reached at.

3. Provision the database

Create the customer's own database (empty). Replace <customer> throughout.

psql -U postgres -c "CREATE DATABASE imms_<customer>;"

Note the connection string you will use — it becomes DATABASE_URL:

postgresql://USER:PASSWORD@localhost:5432/imms_<customer>

4. Get the code and install dependencies

git clone <repo-url> C:\imms\<customer>
cd C:\imms\<customer>

# Backends (reproducible installs)
cd backend                       && npm ci
cd ..\maintenance_call_system\backend  && npm ci

# Frontends
cd ..\..\frontend                && npm ci
cd ..\maintenance_call_system\frontend && npm ci

Both backends and both frontends use npm ci against committed lockfiles — the same installs CI verifies on every change.

5. Configure environment

Each app reads its own .env. Start from the checked-in .env.example in each backend and set, at minimum:

VariableAppValue
DATABASE_URLboth backendsThe customer's connection string from step 3.
JWT_SECRETboth backendsA single strong random value — identical in both apps.
SESSION_SECRETIMMS backendA separate strong random value.
PORTeach4000 (IMMS API), 4001 (MCS API), etc.
CORS_ORIGINSIMMS backendComma-separated frontend origins (e.g. the :3001/:3002 URLs).
CORS_ORIGINMCS backendThe MCS frontend origin (singular).

Frontend URLs are baked at build time, not read at runtime. Set the API/MCS URLs for this customer in the frontend build (see step 7), or the UI will not reach the backend.

Generate secrets

Use unique, unpredictable values per customer, e.g. node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))". Never reuse another customer's secrets. Keep .env files off shared drives and out of version control.

6. Initialize the database schema

The database is empty, so load the base schema, then apply and record every tracked migration:

cd C:\imms\<customer>\backend

# 1) Base schema (creates the initial tables)
npm run migrate:bootstrap

# 2) Apply all tracked migrations to a brand-new DB.
#    --force is required ONLY here: a fresh empty DB legitimately has many
#    pending files, which the first-run guard would otherwise refuse.
npm run migrate -- --force

# MCS schema
cd ..\maintenance_call_system\backend
npm run migrate
Important — the guard

On an existing database that already has migrations applied by hand, do not use --force. Run npm run migrate:baseline once to record them as applied without re-running. --force is only for a genuinely empty new database, as in this fresh-customer case. See PROD_OPERATIONS.md → "IMMS schema migrations".

7. Build the frontends

Bake this customer's backend URLs into the production builds:

cd C:\imms\<customer>\frontend
# Choose/adjust the build target that sets REACT_APP_API_URL + REACT_APP_MCS_URL
# for THIS customer's host (see the build:localhost / build:network scripts).
npm run build:localhost      # or build:network for a networked kiosk

cd ..\maintenance_call_system\frontend
npm run build

If the customer's host/IP differs from the reference, update the API/MCS URL the build script bakes in before building, then rebuild.

8. Start under PM2 and enable boot recovery

cd C:\imms\<customer>
pm2 start ecosystem.prod.config.js
pm2 save                     # snapshot the process list
# Recreate boot resurrection so the stack returns after a reboot
#   (Task Scheduler job running `pm2 resurrect` at logon — see PROD_OPERATIONS.md)

ecosystem.prod.config.js defines all five processes (IMMS/MCS APIs, both IMMS UIs, MCS UI, and the standalone uptime-monitor). Confirm the ports and paths match this customer before starting.

9. Create the first administrator

IMMS is the login authority. Seed one admin account for the customer (via the app's user-creation flow or the seed/admin script), then hand those credentials over securely. All subsequent users are created in-app under an account with CAN_MANAGE_USERS.

10. Verify the instance

  • Health GET :4000/health and :4001/health return 200.
  • UI Load a real hashed asset (not just /) on the frontends — a plain / can 200 via SPA fallback even when assets fail.
  • Login Sign in as the admin; confirm the JWT round-trips and MCS accepts the same session.
  • DB SELECT count(*) FROM imms_schema_migrations; equals the number of backend/migrations/*.sql files.
  • MCS→IMMS Log a part on a maintenance call and confirm the inventory decrement (MCS → IMMS POST /api/v1/parts/usage).

11. Recommended hardening (before go-live)

  • Backups: schedule pg_dump of the customer database on a retention cycle (the reference deploy keeps per-prefix dumps and gates every deploy on a fresh backup).
  • Error tracking: set SENTRY_DSN (Sentry.io or self-hosted GlitchTip) in both backends — off by default until set. Errors then reach a dashboard instead of a console.
  • Uptime alerts: set OPS_ALERT_RECIPIENTS so the uptime-monitor emails on any service going down or recovering. The URLs are LAN-only, so this internal monitor is what watches them.
  • Secrets: restrict access to the .env files; move them to a managed secret store for cloud instances.

12. Ongoing operations

After go-live, this instance is maintained exactly like the reference production:

  • Releases: scripts/deploy.ps1 — backup-gated, tagged, health-checked, with -Ref <tag> rollback.
  • Schema changes: add backend/migrations/YYYYMMDDHHMM_description.sql; the deploy applies it automatically (tracked, transactional, forward-only).
  • Runbook: cutover, deploy, rollback, restore, and troubleshooting all live in docs/deployment/PROD_OPERATIONS.md.
Roadmap notes

This guide is the manual path. Two planned increments make per-customer setup a file rather than a checklist: containerization (build-once images deployed with one compose up) and parameterized provisioning (extracting host/DB/PM2 paths into a config block so one script provisions any box). Adopt them when customer #2 arrives — not before.
